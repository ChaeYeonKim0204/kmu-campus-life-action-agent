> codex 라운드1 반영: [MUST-①] 신뢰된 카탈로그 밖 '전공' 과목이 융합 prefix와 겹치면 primary_base와

> [SHOULD] 매핑을 코드표(A~Z·P*·Q*·R*) 전체 기준으로 재구성(교양필수·기초공통·교양기초→기초교양,

> 포함하므로 전공 계열 키를 기초교양 계열보다 먼저). 프론트 전공 게이지에 필수 미이수 병기.
> '전필/전선' 약어는 코드표에 없어(성적표는 풀네임) 미추가 — 발견 시 후속.

> 배경(사용자 도메인 결정): 성적표의 이수구분은 학적시스템이 그 학생 기준으로 이미 분류한 값.
> "전공선택"으로 찍힌 과목이 본전공이 아닐 일은 거의 없다 — 카탈로그 미수록(구과정·빌드 누락)이라고
> 일반선택으로 강등하는 현행 규칙(verification.py:54-58)이 미래모빌리티 실데이터 오분류의 원인.
> 역방향(성적표 '일반선택'이 융합·다전공 인정과목인 경우)은 코드 기반 융합 매칭이 이미 처리.

## 사실관계 (조사 완료)

1. 강등 발생 지점: `verification.py:57` `if m.status == "aggregate_only" and area == "전공": area = "일반선택"`.
2. **숨은 결합**: `catalog.py:_ISU_TO_AREA`는 substring 매칭이라 "다전공·복수전공·부전공·연계전공·융합전공·타전공" 이수구분이 전부 "전공"으로 흡수됨(실측). 현재는 강등 규칙이 이를 우연히 교정(타전공 과목=카탈로그 미스→일선). **강등만 제거하면 다전공·타전공 이수구분 과목이 본전공 학점으로 오산입되는 역회귀.**
3. 융합 매칭(audit_v2:191)은 코드 prefix 기반 + `requirement_area not in GYO`(교양만 제외) — 전공↔일반선택 변경에 불변.
4. 강등 규칙에 의존하는 테스트 0건. 데모 학생 4명은 전공과목 전부 코드 정확매칭이라 어느 쪽이든 무영향(실측 0건).

## 변경 (2파일 + 테스트)

① `catalog.py _ISU_TO_AREA`: **비제1전공 이수구분을 "전공"보다 먼저 명시 매핑** —
   `"다전공"·"복수전공"·"부전공"·"연계전공"·"융합전공"·"타전공" → "일반선택"` (substring 섀도잉 방지를 위해 dict 앞쪽 삽입; "전공필수"·"전공선택"·"전공기초"는 기존대로 "전공").
② `verification.py`: 강등 분기 제거 — aggregate_only여도 이수구분 "전공*"이면 **전공으로 신뢰**(주석에 도메인 결정 근거·날짜 명시). aggregate_only 플래그는 유지(카탈로그 밖 표시·필수매칭 비대상은 기존과 동일).
③ 테스트(`tests/test_v2_pipeline.py`에 추가):
   - 카탈로그 밖 "전공선택" → area 전공 + aggregate_only (미래모빌리티 증상 회귀 방지)
   - "다전공"/"타전공" 이수구분 → 일반선택 (역회귀 방지 — 섀도잉 수정 검증)
   - 데모 학생 영역 집계 불변(전공 earned 동일)
